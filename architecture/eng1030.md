# ENG-1030: Matching Priority System

## Problem

Right now, our automation runs matches immediately whenever users meet certain conditions, which causes:
- High manual workload
- Poor resource allocation
- Inconsistent user experiences

## Solution

A priority system ensures the automation focuses on the users who need matching the most.

---

## Priority Tiers

| Tier | Label | Who |
|---|---|---|
| 1 | **Ultra Fast** | Users who asked for updates (chatbot) · Reactivated users |
| 2 | **Fast** | Recently rejected by others · Waiting > 1 week with ≥ 1 historical match · Date cancelled after scheduling · Match expired (`PickTimeFailed` / `Failed - Expired`) |
| 3 | **Default** | Everyone else — no label needed |

## Changes to `PriorityUserService`

Signature change:
```ts
setUserPriority(userId, tier: "UltraFast" | "Fast", reason: string, setBy = "system")
```

Logic:
- Respect tier ordering — `UltraFast > Fast`. If the user already has an active `UltraFast` record, do not downgrade to `Fast`.
- Deactivate any existing active priority record before creating the new one (current behavior).
- Always write a `priority_history` record regardless of whether the update was skipped (log the attempted reason for observability).

### Fast — Rejected by others
**File:** `src/match-status/match-status.service.ts`, `markNotGoing()` (line 248)

`markNotGoing(matchId, userId, setBy, opts)` marks the *calling user* (`userId`) as the canceller and calls `updateMatchStatus(match, "Failed - Refused", ...)`. The remaining (non-cancelling) user's index is `1 - userIndex` (matches always have exactly 2 users). That user goes to `Waiting` via `updateMatchStatus → updateUserStatus` (line 173 in the `case "Failed - Refused"` branch).

**Where to hook:** After `updateMatchStatus` resolves (line 294), identify the other user:
```ts
const otherUserId = match.users[1 - userIndex];
await this.priorityUserService.setUserPriority(otherUserId, "Fast", "rejected_by_match");
```
Only set if `opts?.initiatorStatus` is `undefined` (i.e., normal rejection — not the case where the canceller is Pausing/Deactivating via `pauseMatchedUserAccount` or `userAccountDeactivation` tools). When a user pauses/deactivates through a match, it is their own choice, not a rejection signal for the other user. The "rejected" signal should only fire for a clean `markNotGoing` with no `initiatorStatus` override... though treating `Paused`-initiated cancellations the same as rejection is debatable. For now: only fire on `opts?.initiatorStatus === undefined`.

---

### Fast — Date cancelled after scheduling (`DateCancelled`)
**File:** `src/match-status/match-status.service.ts`, `markDateCancelled()` (line 310)

Same pattern as `markNotGoing`. The `userId` passed in is the canceller; `match.users[1 - userIndex]` is the user who had their confirmed date fall through. This is treated the same as a rejection — a date that was scheduled and then cancelled on them is functionally equivalent to being rejected at the late stage.

Both users go to `Waiting` on `DateCancelled` (line 169–173 in `updateMatchStatus`). Only the non-cancelling user gets the priority bump:
```ts
const otherUserId = match.users[1 - userIndex];
await this.priorityUserService.setUserPriority(otherUserId, "Fast", "date_cancelled_by_match");
```

---

### Fast — Match expired (`PickTimeFailed` / `Failed - Expired`)
**File:** `src/match-status/match-status.service.ts`, `updateMatchStatus()` (line 123), inside the `isCompletedState` block.

**`Failed - Expired`** (line 172): all users unconditionally go to `Waiting`. No engagement filter exists here — everyone is a candidate for `Fast`.

**`PickTimeFailed`** (line 175–198): users go to `Waiting` unless their `acceptanceStatus` was `null` in **all of their last 3 completed matches** (not just the current one). So users reaching `Waiting` via `PickTimeFailed` already passed a historical-engagement filter. They are all candidates for `Fast`.

Note: the pausing condition is a **cross-match pattern check** (3 matches), not just "didn't engage in this one". A user who ghosted this match but engaged in prior ones still lands in `Waiting` and should get `Fast`.

**Where to hook:** In `updateMatchStatus()`, after `updateUserStatus(userId, userStatus, setBy)` is called (line 208), when `userStatus === "Waiting"` and `newStatus` is `"PickTimeFailed"` or `"Failed - Expired"`:
```ts
if (
  (newStatus === "PickTimeFailed" || newStatus === "Failed - Expired") &&
  userStatus === "Waiting"
) {
  await this.priorityUserService.setUserPriority(userId, "Fast", "match_expired");
}
```

---

### Fast — Waiting > 1 week with ≥ 1 historical match (existing ticket item)
Requires a new scheduled job — no existing time-based hook for this.

**Suggested location:** New `@Cron` method in a scheduler service (e.g. `src/scheduler/` or a new `src/priority-user/priority-user-cron.service.ts`).

**Query logic:**
1. Find all active `matching_statuses` docs where `status === "Waiting"` and `createdAt < now - 7 days`
2. For each userId, check if they have at least 1 completed match in the `matchings` collection (`status` in `CompletedMatchStatusValues`)
3. Call `setUserPriority(userId, "Fast", "waiting_over_1_week")` for each (no-downgrade rule in service handles UltraFast users automatically)

Run once per day.

`removeUserPriority()` is already called in `match-status.service.ts` line 445 when `newStatus !== "Waiting"` (i.e., user got matched, paused, deactivated, etc.). 

**Change:** update `removeUserPriority` to also write a `priority_history` record with `tier: "Default"` and a reason derived from the new status (e.g. `reason: "status_changed_to_Matched"`).

## Internal Frontend

`getPriorityUsers()` in `src/internal/user/internal-user.service.ts` (line 924) currently returns a flat `string[]` of user IDs. Needs to return `{ userId: string, tier: "UltraFast" | "Fast", reason: string, setAt: Date }[]` so the AI Matchmaker page can label and sort.

Sorting: `UltraFast` first → `Fast` → `Default`. Within each tier, sort by `setAt` ascending (oldest in tier = been waiting longest).

## Open Questions

- For `markNotGoing` with `opts.initiatorStatus === "Paused"` (user paused through `pauseMatchedUserAccount` tool): should the other user still get `Fast`? The pause was the user's own choice, but from the other user's perspective it's still a rejection. Decision needed.
- Should `Failed - Expired` get a per-user engagement check before setting `Fast`, or treat all as equal? Currently no check exists; adding one would require inspecting `acceptanceStatus` on the match.
- Manual admin override of priority from the internal dashboard — out of scope for now.
